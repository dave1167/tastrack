# H2 application-wide tenant lifecycle enforcement

## Enforcement design

Substantive tenant writes call `tenantLifecycle.requireWrite` as the first Server Connect execution step. The module reloads the tenant from the database on every request, checks active dates and lifecycle status, and validates the authenticated user's active membership in that same tenant. Browser-supplied tenant identifiers are not used.

The endpoint inventory and classification are generated by `node scripts/h2-lifecycle-inventory.js --write`; the resulting matrix is `app_docs/TENANT_LIFECYCLE_ENDPOINT_MATRIX.md`.

Notification/chat read markers and the user's availability are explicit benign-state exemptions while the tenant remains readable. Authentication/session writes retain their existing policy. Platform administration retains its separate platform-admin authority so authorised staff can extend or reactivate tenants.

The Nylas webhook resolves tenant identity from the stored grant connection before calling the same lifecycle decision. Events for blocked tenants are recorded as `ignored_lifecycle` and acknowledged without ingesting communications. The OAuth callback is checked before exchanging/storing a mailbox grant.

Suspended and closed tenants are excluded from login tenant selection. Expired/read-only demo and trial tenants may review existing information, receive an application-wide banner, and are blocked from substantive changes server-side.

## Wappler schema refresh

H1 changed the development database schema. In Wappler, select the **Development** target, open **Database Manager**, select connection **db**, and use **Refresh/Reload Schema from Database**. Review the detected lifecycle and scenario tables/columns, then save the project. Do not push a stale local schema definition back to the database.

This refresh is a manual Wappler metadata step; runtime enforcement does not depend on hand-editing `.wappler/targets/.../db.json`.

## Forward migration baseline

The H1 schema as applied on 18 August 2026 is the documented baseline for lifecycle/scenario development. Historical changes have not been fabricated or marked as previously executed. Every schema change after this baseline must be created as a new dated Wappler migration, reviewed, applied through the normal migration runner in each environment, and verified in Wappler's migration history before deployment proceeds.

Environment order is local development, staging, demo, then live. Never reuse development data or production credentials in another environment.
